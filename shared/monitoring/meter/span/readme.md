### SpanMeter
1. 기존의 레저부아 미터기를 보완하기 위하여 다시 설계한 미터기
2. 기존 레저부아 미터기의 단점은 다음과 같음.
    - 타임 윈도우와 그에 따른 시간별 변화율을 반영하지 못함.
    - 어찌저찌 시간을 기록시켜서 강제로 시간별 변화율 반영하게 하면, 매번 정렬이 들어가게 됨.
    - 즉, "시간별 정렬"을 빠르게 하는 것이 핵심.
3. 이를 해결하려면, 처음부터 '타임버킷'형태로 만듦으로써 자동 정렬을 시킬 수 있음
    - 이 경우엔 타임버킷이 유발하는 "용량 증폭"이 문제가 됨.
    - 이에 대한 방안은 LSM의 아이디어에서 찾았음
    - 버킷별을 계층화, 계층에 따른 버킷의 span을 지수적 증가, 레벨의 버킷 수 제한할 시에
    - 시간의 증가에도 불구하고 타임버킷 개수를 log수준으로 줄일 수 있음. 사실상 무한임.

### 요구 사항
1. 시간별 변화율을 담을 것. 
2. 반-영구적으로 돌아가는 프로세스에서 메모리 상한 혹은 준-상한을 지닐 것.
    - 실제 구현에선 스케치를 통해 확실한 메모리 상한을 걸었음.
3. 병렬 안전할 것.
4. 대규모 데이터에 대해 고속 분석이 가능할 것.
5. 요구 지표
    - name별 평균값, 총 호출횟수, 총 시간
    - p50,p95,p99
    - 시간별 span 변화율
    - "미터기 자신의 큐" (비동기 큐잉으로 지표값 레코딩 결정했기 때문. 미터기가 병목이 되어선 안됨.)

### 구현 아이디어
1. 버킷의 Span은 level에 따라 2의 지수 승으로 증가
    - 각 Level의 병합을 조정하면 "임의의 정수 Span"값을 언제든 log 횟수로 도출 가능.
    - 한 줄 증명: 이진수가 모든 수를 표현 가능하므로, 이진 전개는 참임.
    - 이진 전개 아이디어임.
    - CS에선 이걸 dyadic cover라고 일컬음.
2. 스케치 기반 Merge
    - 타임버킷을 통해선 시간 윈도잉이 가능. 그러나 "윈도우 내에서" p99,p95분석 시엔 스케치가 용이
    - 윈도우 머징 시, 윈도우를 스케치로 만드는 것.
    - 메모리 상한, 고속 연산, 병렬 환경에서 빠름
3. (큐잉 vs 샤딩-스트라이프) for 병렬연산
    - 병렬적으로 지표가 들어오는 상황에서 미터기에 대한 설계 고민이 있었음
    - AI는 샤딩-스트라이프 구조를 샤딩-스트라이프 구조는 결국 다시 머지비용-관리 복잡도 증가시킨다고 봤음.
    - 애초에 "Span"을 기록하는 건데, 여기에 수백만 tps가 몰리지도 않을 것임. 몰린다 해도 배칭으로 충분히 가능.
    - 결국 중요한건 병렬 환경에서 "쓰기 경합"을 줄이는 것.
    - 근데 그럼 그냥 채널링하면 되지 않나? 싶었음. 또한, 채널+배칭으로 해도 미터기가 Stat을 출력하는 데에는 아무 문제가 없지.
4. RCU (튜닝용)
    - 솔직히 여기서부턴 과할 수 있음
    - level 0의 가장 최신 타임버킷을 조회할 때에, 이를 "일관된 상태로, 지연 없이" 읽기 위해 RCU사용을 선택함
    - 비약적인 성능 향상을 기대하진 않음
    - 지연 없는 읽기라곤 하지만 그건 L0한정이고, 결국 병합 동안은 미터기 락 혹은 중단-지연이 걸림.
